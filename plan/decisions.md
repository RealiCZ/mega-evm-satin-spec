# Satin Specification — The Owner's Decisions

The owner's answers to the questions of [questions.md](questions.md), decided on 8 November 2026 (QG-07, and QH-01 and QH-02, raised by the review of the written section, on 9 November 2026), as the Satin section is written from them.
Each line gives the question, the decision, and the reason in one line; where a decision changes an implementation, the change is listed in [changes-evm.md](changes-evm.md) for the execution pages and in the block pages' own list for the rest.

## The rule for the QE items

Among the QE items, where the two implementations differ, Satin follows the behaviour of evm2 — implementation (b) and evm2 upstream — and implementation (a) changes where it differs.
This rule covers the QE items only; every other question follows its recommendation unless the table says otherwise.

## The Rex6-parity decisions (QI)

On 9 November 2026 every Satin rule on system contracts and on block handling was compared with Rex6's specification and code, and the owner decided, item by item, what Satin keeps of its own changes, what returns to Rex6, and which Rex6 defects Satin fixes.
These items arose from that comparison, not from [questions.md](questions.md), so they have no entry there; their implementation changes are listed in [changes-blocks.md](changes-blocks.md) and [changes-evm.md](changes-evm.md).

The rule they follow, as the owner set it: a Rex6 defect is fixed; a requirement Rex6 makes mandatory Satin does not relax; and Satin adds nothing of its own to the system contracts unless the addition is stated explicitly — refined the same day: Satin may change Rex6 where the change is more reasonable; a relaxation is unacceptable only when its side effects cannot be eliminated, and one whose side effects extra defences or operations can remove is brought to the owner with that analysis; every change is stated in the Satin pages as a change, with its reason, and every Rex6 defect Satin fixes is labelled `**Rex6 defect fixed.**` in the page's Rationale.

| Item | Decision | Reason |
| --- | --- | --- |
| QI-01 | Rex6's Oracle persistence is Satin's (`SATIN-ORCL-012`): a value the oracle service gives a read MUST be persisted by a Mega System Transaction calling `setSlot`/`setSlots`, ordered before the reading transaction, unless the reading transaction's own writes explain it (the slot's present value at the read is the transaction's own earlier write of that value, one no revert took back); validators run no service and read the slot; no record of the service's answers on outcomes or beside the block (`SATIN-WIT-015` retired, the recording sentence of `SATIN-ORCL-002` removed). Labelled Rex6 defect fix: a transaction is left out only when a slot it reads has no value that, written before it, reproduces all its reads of the slot, its own writes included (`SATIN-ORCL-013`): read, hint, read, answered two values, is left out; read 7, an authorized write of 8, read 8 is included, 7 persisted before it and no write of 8. Owner: agreed to all of it, to be done; on the exclusion's scope, 9 November 2026, the reproducibility criterion adopted: "a transaction is left out only when no value written before it reproduces all its reads of the slot, its own writes included; read-hint-read is the example" | A mandatory Rex6 requirement Satin had relaxed into an optional record; the read-hint-read case is a latent Rex6 defect; a value the transaction's own write explains needs no front-running write, since the replay reads that write |
| QI-02 | In the deposit-only block in which Satin activates the node asks the oracle service nothing; every Oracle read pushes the slot's on-chain value (`SATIN-ORCL-005`, `SATIN-BASE-008`). Owner: all three as recommended | No Mega System Transaction can persist a value in that block |
| QI-03 | Rex6's per-block system-contract deployment is Satin's (`SATIN-SYSC-003`, `SATIN-REG-008`, `SATIN-REG-009`; `SATIN-ACT-006` retired): the five flat contracts installed when missing and their code rewritten when it differs (read-only entry when right); the SequencerRegistry deployed and seeded from the Rex5/Rex6 bootstrap keys only when absent or without code, migrated in place only from version 1.0.0, foreign code refusing the block; registry apply before its deployment. Satin may be active from genesis as Rex6 may (`SATIN-ACT-012`), the EIP-2935/EIP-4788 block-0 exceptions included (`SATIN-PBLK-003`). The activation block checks only the EIP-7997 factory (`SATIN-ACT-005`, QC-01 kept for the factory); deposit-only activation (QB-02) kept. Owner: if it can be supported, Satin is to be supported from genesis, and this part need only stay as it was before; option X, agreed to all of it, to be done | Restores Rex6's availability and repair of the contracts and makes genesis activation possible |
| QI-04 | The Oracle prose follows its bytecode, no new restriction: `SATIN-ORCL-011` and `SATIN-BASE-008` state only the immediate-caller authorization after the body; `SATIN-ORCL-002` distinguishes another account's delegation from the Oracle's own; `multiCall`'s empty-revert-data fallback stays stated | The node adds no rule to the contract's |
| QI-05 | A `sendHint` is admitted without a value condition, as in Rex6 (`SATIN-ORCL-006`, `SATIN-ICPT-003`). Owner: all seven restored as recommended (QI-05 to QI-08, QI-10 to QI-12) | A relaxation of nothing; restoring changes no other rule |
| QI-06 | An Oracle `SLOAD` with too little gas for its cold access still loads the slot, asks the service and marks the read, the mark surviving the opcode's failure, as in Rex6 (`SATIN-ORCL-004`, `SATIN-DET-003`, `SATIN-WIT-012`) | Rex6 states the surviving registration as a requirement |
| QI-07 | The timestamp snapshot is above the parent block's timestamp, and never below an earlier snapshot, across blocks too, as the node guarantees (`SATIN-HPTS-001`); text only, no engine change | The node Rex6 runs on keeps both |
| QI-08 | A refused volatile read costs nothing, and the opcodes volatile whatever their operands are refused before their operands are checked, as in Rex6 (`SATIN-MAC-003`, `SATIN-MAC-004`) | Rex6 states both as intended semantics |
| QI-09 | The `keylessDeploy` call's arguments are decoded before it is recognized; a call whose arguments do not decode runs the bytecode and pays no dispatch overhead, as in Rex6 (`SATIN-ICPT-006`, `SATIN-KEY-005` step 3) | Rex6's interception boundary |
| QI-10 | The live system address is resolved once per block, after the pre-block steps, its read a read-only pre-block state in the witness; no transaction reads or warms the registry for its classification (`SATIN-REG-002`; `SATIN-REG-003` and `SATIN-SCHED-013` retired) | Rex6's resolution; the per-transaction read added warmth and reads Rex6 does not have |
| QI-11 | A registry that is absent, holds other code, or names no system address makes the block invalid, as in Rex6 (`SATIN-REG-004`) | Rex6 fails closed on a corrupted registry |
| QI-12 | Mega System Transactions are held to the block's data-size, KV-update and state-growth budgets and to building policy, as in Rex6 (`SATIN-BLK-003`, `SATIN-BLK-006`, `SATIN-BLK-007`, `SATIN-BLK-011`, `SATIN-BLK-013`); deposits stay exempt (a labelled Rex6 defect fix) | A Mega System Transaction is optional; its reader is left out with it |
| QI-13 | Deposits and Mega System Transactions pay history gas like any transaction; the pre-block system calls stay exempt; system-originated work keeps the minimum-bucket state pricing (`SATIN-HIST-016`, `SATIN-HIST-022`, `SATIN-MST-008`, `SATIN-MST-010`, `SATIN-DEP-001`, `SATIN-TAKE-012`). Owner: they should be charged, since in principle whatever is stored is paid for; on the system calls: those can be exempt | What the chain stores is paid for; a pre-block call appends no transaction |
| QI-14 | Satin follows the Optimism base forks it requires (Karst, Jovian and their predecessors) with their whole transaction and block rule set (`SATIN-BASE-001`). Owner: all three as recommended | A partial base is no OP Stack node |
| QI-15 | The L1 block contract is read on demand, as the base layer's fee computation needs it: no read of all five slots in every block and no failure on a slot nobody reads (`SATIN-WIT-011`, `SATIN-WIT-003`, `SATIN-PBLK-003`, `SATIN-BASE-010`); the fix that every slot a fee computation reads is in the witness is kept and labelled. Owner: all three as recommended | Rex6's reads; only the witness hole was a defect |
| QI-16 | Kept, each stated in its page as a change from Rex6 with its reason: no oracle service in system calls; a hint over the data-size limit a stop of its call; `BLOBHASH` not volatile (owner: this was the ruling made at the time, and it should never have triggered detention); `remainingComputeGas()` bounded by the caller's regular gas; native KeylessDeploy — `ORIGIN`/`GASPRICE`, warmth, frame budgets and detention, start charges and `gasUsed`, the four errors, the live signer nonce (owner: this is the design, it stays, and it also keeps the inspector simple); the chain-id check on; each pre-block step committed before the next; the fixed body and settlement records, no caller KV, no fee-recipient growth (owner: use the new ones); the 98/100 reservoir share for protocol work too; a deposit's limit stop a revert; reads gas skipped not in the witness; the block hashes served exported, not the cache. Owner on the kept bucket: a restoration that does real harm is not worth considering | Each is more reasonable than Rex6's rule and has no side effect that cannot be removed |
| QI-17 | Every Rex6 defect Satin fixes is labelled `**Rex6 defect fixed.**` in its page's Rationale with the input on which Rex6 goes wrong: the Oracle read that did not load the slot, the empty-code keyless deposit, the keyless read failure as a result, the keyless fallback prose, the unexported sandbox bucket, the early-failed deposit's uncounted caller, the deposit refused by the packing budgets, the malformed conditionally volatile opcode, the missing L1 overhead slot, the fatal pre-block database error as an invalid block, the deposit-marker prose, the saturating due-change precheck, the two-value Oracle transaction, the deposit from a rotated system address, the phantom keyless signer growth | A fix of a Rex6 defect is stated as one |
| QI-18 | Omissions restated: the SequencerRegistry's layout is append-only after slot 13 (`SATIN-REG-001`); a configuration that schedules Satin climbs the Mega spec ladder, only the alias rungs omissible (`SATIN-ACT-011`) | Rex6 requirements Satin had not restated |
| QI-19 | No oracle service for deposits, Mega System Transactions or system calls: during any of them the node asks the oracle service for no value, and an Oracle read pushes the slot's on-chain value and is loaded, priced and marked like any Oracle read (`SATIN-ORCL-005`); only a transaction that is neither a deposit nor a Mega System Transaction is served. Decided by the owner on 9 November 2026, after a check of the published text against the implementations | As published, a deposit's served read had to be persisted by a Mega System Transaction before the deposit, which no block can order, and the deposit then left out, which no block may do; Rex6's node serves none of these |
| QI-20 | `SATIN-ORCL-012`'s persistence is worded on what a read pushed: the sequencer MUST persist every value of the service a read pushed, unless the transaction's own writes explain it, and MAY persist a value the service gave a read that pushed nothing — a read made before its charge whose frame then ran out of gas at the `SLOAD` or was stopped at gas detention's crossing — as long as the slot still reproduces the transaction's reads; `SATIN-ORCL-013` counts only the reads that pushed a value. Decided by the owner on 9 November 2026 | The replay of a read that pushed nothing pushes nothing, whatever the slot holds, so it needs no value |

## Added requirement

The Satin section has one page that lists every Satin rule — its id, one line, and a link to its home — so a reader never has to open a Rex-era page; the Satin section restates every rule it keeps, and none says "same as Rex".
